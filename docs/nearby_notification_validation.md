# 近接通知 v1 検証手順

この文書は、`作成案/新しいフォルダー/chikabell_nearby_notification_spec_v1.md` の実装をPixel 10aで検証するための手順です。座標、地点名、通知本文などの個人情報は検証記録へ転記しません。

## 自動検証

```powershell
.\gradlew.bat testDebugUnitTest lintDebug assembleDebug assembleDebugAndroidTest
git diff --check
```

接続端末が認証済みの場合:

```powershell
adb devices -l
.\gradlew.bat connectedDebugAndroidTest
```

Room 10→12 migration、状態・休止期限・最終有効測位時刻の永続化、短時間検証ポリシー、通知文面、複数地点集約、同一接近抑制、重複検証claim、短時間確認サービスの終了を確認する。

2026-07-18時点では、Pixel 10a / Android 17でJVMテスト82件と端末テスト7件が成功している。これは下記の実地シナリオを代替しない。以後テストを追加した場合は、最新の実行結果で件数を更新する。

## バックグラウンド取得方式

- 1地点につき1ジオフェンスを維持し、100地点上限を保つ。
- freshな活動状態に応じて単一の事前確認リングを置換し、UNKNOWNまたはstale時は車両側の広いリングを使う。
- 短時間検証中と通知半径の確認リング待機中は、活動切替による一括半径更新から除外する。検証終了またはEXIT後に、その時点の活動帯で通常リングへ戻す。
- 外周ENTER後は、1地点ごとではなくPlay servicesから届いた1イベント全体を最大3分の共通予算で処理する。通知成立、物理的に不可能な跳躍、継続的な遠ざかりを検出した時点で位置更新を終了する。
- 最大3分で通知成立しない場合は、同じrequest IDを通知半径の確認リングへ置換する。確認リングからの追加検証は1回だけとし、不成立時は通常リングへ戻して連鎖起動を防ぐ。
- 通知半径5,000mでも同一接近中の再通知を避けるため、内部の事前確認リングは再有効化距離7,500mを使う。ユーザーが設定する通知半径上限は5,000mのままとする。
- 通知後は同じrequest IDを通常の活動別事前確認リングへ戻す。常時複数リングは登録しない。

## 地図の製品方針

- 「地図を見る」は代表候補（最寄り候補）を外部Googleマップで開く。
- アプリ内にMaps SDK、APIキー、全候補の地図表示を追加しない。通知後の継続測位やナビゲーション化を避けるための意図的な製品判断である。

## 診断データの保持と削除

- 地点ごとの検証診断は、最終検証状態更新と最終有効測位を分け、最新値だけを上書き保存する。有効な測位がない失敗で、過去の最終有効測位時刻を偽の成功時刻に置き換えない。
- 通知履歴は最大1,000件かつ180日、ジオフェンス登録・復元試行は最大200件かつ90日、ヘルスチェックは最大500件かつ90日で自動削除する。
- 通知履歴は履歴画面の「すべて削除」で即時削除できる。登録・復元・ヘルス診断は上記上限による自動pruneを削除方法とし、詳細な位置履歴を保存しない。

## 端末保護

1. 対象はPixel 10aとする。
2. 検証前後に次を読み取り、値を変更しない。

   ```powershell
   adb -s <PIXEL_SERIAL> shell settings get system accelerometer_rotation
   adb -s <PIXEL_SERIAL> shell settings get system user_rotation
   ```

3. 通常起動に`adb shell monkey`を使わない。
4. 更新インストールが必要な場合は、既存データを保持する`adb install -r`だけを使う。
5. アンインストール、データ消去、端末再起動、権限やバッテリー設定の変更は、ユーザーの明示承認なしに行わない。
6. 活動認識の許可後は、設定画面の「現在の活動」と更新時刻、および短時間確認中の診断理由を確認する。

## 実地シナリオ

各シナリオで、通知有無、重複数、事前確認開始から通知までの時間、最終判定理由、accuracy、実測速度、検証終了状態を確認する。

1. 徒歩で通知距離へ接近する。
2. 自転車相当速度で通知範囲を通過する。
3. 車両相当速度で通知範囲を通過する。
4. 境界を往復し、同一接近中に通知が増えないことを確認する。
5. 位置精度が悪い場所で、数値距離が表示されないことを確認する。
6. 重なる複数地点で1通知に集約されることを確認する。
7. 「12時間休止」で通知に含まれた全地点が休止することを確認する。
8. アプリ内から休止を解除できることを確認する。
9. 端末時計やDBを変更せず、実際に12時間の期限が切れた後、地点が自動で通常監視へ戻ることを確認する。未実施の場合は期限切れ未検証として記録する。
10. 十分に退出して再接近した場合だけ再通知されることを確認する。
11. 画面OFF、プロセス終了後、バッテリーセーバー中の動作を個別に確認する。
12. 位置情報OFF、通知権限拒否、位置権限拒否でクラッシュせず理由を確認できることを確認する。
13. 通知後に追加測位や検証状態が残らないことをログと診断表示で確認する。
14. 外周ENTER時に通知範囲外でも、再ENTER操作なしで3分以内に内側へ入ると一度通知されることを確認する。
15. 3分以内に内側へ入らなかった後、確認リングへ進入すると一度通知され、通常リングへ復帰することを確認する。
16. WALKING、ON_BICYCLE、IN_VEHICLE、UNKNOWNの切替後も登録地点数が増えず、1地点1request IDのままであることを確認する。
17. 複数地点が同一イベントに含まれても、検証Foreground Serviceがイベント全体で3分を超えず終了することを確認する。
18. 確認リングで通知条件が成立しない場合、追加検証が1回で終了し、確認リングの再登録を繰り返さないことを確認する。
19. 通知半径5,000mの地点で、半径境界の位置ジッタだけで再有効化されず、7,500m付近のEXIT後に再通知可能になることを確認する。
20. 短時間検証中に事前確認リングからEXITした場合、次の3分タイムアウトを待たずに位置更新コールバックとForeground Serviceが終了し、`MONITORING`へ戻ることを確認する。
21. 通知半径の確認リング待機中に活動状態が切り替わっても、確認リングが通常の広いリングで上書きされず、内側へのENTERを検証機会として維持することを確認する。
22. EXITから60秒以内に正当なENTERが続いた場合、EXITを同種イベントの重複とみなさず、新しい短時間検証を開始することを確認する。

## 実地証拠の記録様式

座標、地点名、通知本文、移動経路は記録しない。各シナリオにつき次の1行を作成する。

| 日時 | シナリオ | Android/端末 | 通知数 | 重複数 | 開始→通知(秒) | 検証継続(秒) | 測位回数 | 最終状態 | 判定・抑制理由 | 結果 |
|---|---|---|---:|---:|---:|---:|---:|---|---|---|
| YYYY-MM-DD HH:mm | 徒歩/自転車/車両/境界/12h | Android 17 / Pixel 10a |  |  |  |  |  |  | 個人情報を除いた診断理由 | PASS/FAIL/UNVERIFIED |

### 共通合格基準

- 1回の接近で対象通知は1回、重複数は0。
- 通知後とEXIT後は検証状態が残らず、`NearbyVerificationService`が停止する。
- 検証時間は1イベント全体で3分以内。通知成立、EXIT、継続的な遠ざかりでは上限を待たず終了する。
- 精度不足時は数値距離を表示せず、偽の最終有効測位時刻を記録しない。
- 12時間休止中は短時間検証を開始せず、期限切れまたは手動解除後にのみ`MONITORING`へ戻る。
- 通知半径の境界揺れでは再有効化せず、十分なEXIT後にのみ再通知可能になる。

### シナリオ別判定

| 必須シナリオ | PASS条件 | 現在の証拠 |
|---|---|---|
| 徒歩 | 通知範囲で一度通知し、通知後に測位を終了 | UNVERIFIED |
| 自転車相当 | 通過中に一度通知し、測位間隔が自転車帯 | UNVERIFIED |
| 車両相当 | 高速通過中に一度通知し、測位間隔が車両帯 | PARTIAL: 通過地点1件の通知と重複防止は確認。目的地点のEXIT直後ENTER抑制を修正し、再試験待ち |
| 境界揺れ | 境界往復で重複通知0、十分なEXIT後のみ再有効 | UNVERIFIED |
| 12時間休止 | 実時間12時間は検証・通知せず、時刻/DB改変なしで自動復帰 | UNVERIFIED |

### 2026-07-18 車両移動の実地証拠（匿名化）

- 車両移動中、匿名化した通過地点1件で12:28:09に通知が1回POSTEDとなった。確認位置は十分内側、通知後は`REARM_WAIT`となり、7分後のDWELLは「同じ接近中」として抑制された。通過地点については、通知成立と同一接近中の重複防止を確認した。
- 目的地点は12:21:06にENTERを受信していたが、29秒前のEXITを同種の重複イベントと誤判定し、短時間検証を開始しなかった。原因をEXIT後の再有効化と60秒重複窓の交差と特定し、EXIT直後の次回ENTER/DWELLだけ重複窓を迂回する修正と回帰テストを追加した。修正版での車両再試験は未実施。
- 実通知は`nearby_place_alerts`へ正常にPOSTEDされ、チャンネルは通常重要度、既定通知音、ユーザー固定なし、おやすみモードOFFだった。無音設定は短時間確認Foreground Service専用チャンネルだけであり、実通知を無音化するアプリ不具合は確認できなかった。通知時点の車載Bluetooth経路や瞬間的な端末状態は遡及確定できないため、通知音の実機再現は未検証。

## 再起動ゲート

端末再起動はユーザー承認後にのみ行う。再起動前後で次を確認する。

- 12時間休止期限が維持される。
- `REARM_WAIT`が失われず、同じ接近中に再通知されない。
- 監視が復旧する。
- 3分を超えた古い`VERIFYING`は`MONITORING`へ回復する。

## 完了判定

自動テスト成功だけでは完了としない。徒歩・高速移動・境界揺れ・休止・再起動・画面OFF・権限拒否は別々の証拠として記録し、未実施項目は明記する。
